    Tool Registry: Research, Design, and Implementation Plan¶

    Context: Inclusive Agentic Architecture — Phase 2 deliverable for Issue #173

    1. Problem Statement¶

    The Inclusive Architecture defines a Tool Library used by the Agent Orchestration layer to perform deterministic I/O operations — data retrieval, writes, vector search, object storage, and messaging. The goal is to establish a governed, extensible tool registry that:

    • Is entirely free (no paid SaaS)
    • Gets the foundation right from day one (no "upgrade later" technical debt)
    • Reuses community-maintained MCP servers where they exist
    • Exposes common abstractions for Postgres, MongoDB, Azure Blob, Qdrant, Azure AI Search, LanceDB, and messaging (Azure Queue, Kafka, RabbitMQ)
    • Keeps secrets and credentials completely isolated from the LLM context

    2. Industry Landscape¶

    2.1 How Leading Companies Approach Tool Registries¶

    Company Approach Key Insight
    Anthropic MCP Protocol + public MCP Registry (federated) Sub-registries for enterprise private use; tool schema is JSON Schema; tools/list RPC for runtime discovery
    Microsoft Azure API Center (MCP server catalog) + Semantic Kernel Plugins Plugin = named group of related tool functions; Azure API Center generates OpenAPI defs from registered MCP servers
    Google ADK with native MCP + Agent2Agent (A2A) protocol Agent Cards for capability discovery; native Qdrant and OpenAPI tool integrations
    OpenAI Function Calling (JSON Schema) + AgentKit Connector Registry Strict schema enforcement (strict: true); tool count kept under 20 per call for accuracy
    Salesforce Agentforce + A2A for cross-org agent interop Lifecycle management as first-class concern; governed agent registry

    Patterns common to all: - Tool metadata (name, description, JSON Schema, version, owner) is stored separately from tool implementation - Tools are stateless — all context injected as parameters; connection and credentials injected at registration time, never in the LLM context - Tool count per agent call kept under 10–20 — more tools degrade LLM tool selection accuracy - Semantic Versioning (MAJOR.MINOR.PATCH) is standard; any breaking schema change = MAJOR bump; model upgrades = MAJOR bump

    2.2 The Emerging Open Standard: MCP (Model Context Protocol)¶

    As of early 2026, MCP is the de facto open standard for agent tool registries:

    Metric Value
    Monthly SDK downloads 97M+ (November 2025)
    Governance Linux Foundation (AAIF) — co-founded by Anthropic, OpenAI, Block
    Framework support Anthropic Claude, OpenAI AgentKit, Semantic Kernel, Google ADK, LangChain, CrewAI
    Protocol base JSON-RPC 2.0 over stdio (local) or Streamable HTTP (remote)
    Tool discovery tools/list RPC; .well-known/mcp.json passive discovery
    Registry entries ~2,000 servers, 407% growth since September 2025 launch

    MCP defines tools as stateless callable functions with JSON Schema input contracts — exactly aligned with our architecture's definition of tools as "deterministic connectors or adapters that perform actions or I/O without reasoning."

    2.3 Registry Option Evaluation¶

    Three viable free/open-source approaches exist:

    Option A: Build custom lightweight registry (FastAPI + Postgres catalog)

    A minimal FastAPI service storing tool metadata (name, description, schema, version, endpoint) in Postgres, with a /tools discovery endpoint. Each tool server is a standalone MCP server or Python function.

    • Pros: Full control, minimal dependencies, built in days
    • Cons: Auth (OAuth/Entra), RBAC, audit logging, and multi-server aggregation all require custom builds; does not compose with the MCP ecosystem; ongoing maintenance burden

    Option B: LangChain / LangGraph Tool Ecosystem

    Tools implemented as LangChain @tool decorators registered into a LangGraph ToolNode. Large ecosystem of pre-built integrations (Postgres, MongoDB, Qdrant, Azure AI Search all have LangChain community tools).

    • Pros: Large pre-built ecosystem; tight LLM integration
    • Cons: Heavy LangChain dependency; not MCP-protocol-compatible; less aligned with our event-driven architecture; proprietary abstraction rather than an open standard

    Option C: MCP-native stack with mcp-gateway-registry

    All tools exposed as MCP servers (using fastmcp or the mcp Python SDK). A single gateway (agentic-community/mcp-gateway-registry, Apache 2.0) handles auth, RBAC, audit, and multi-server aggregation behind one endpoint.

    • Pros: Industry-standard protocol; universal framework compatibility; built-in auth/RBAC/audit; dynamic tool discovery; free; extensible; vendor-maintained community servers available for most target systems
    • Cons: Gateway adds ~2 days of setup overhead vs a flat list of standalone servers

    2.4 Decision¶

    Option C is selected. The MCP-native stack with mcp-gateway-registry from day one. The reasoning:

    • Auth (OAuth / Entra), RBAC, and audit logging are structural requirements that cannot be retrofitted without rewriting every tool server. Building them once at the gateway layer eliminates this risk entirely.
    • We have 5+ target tool servers. A gateway that aggregates them behind a single endpoint is essential for the orchestration layer to remain stable as tools are added.
    • Compliance requirements (EU AI Act high-risk logging, A4I audit trail) require a single enforcement point — the gateway is that point.
    • The ~2 day setup overhead is trivially smaller than the cost of re-implementing auth and audit logging across each server individually.

    4.2 Adoption Strategy¶

    Use directly (minimal wrapping needed): - microsoft/mcp (Azure MCP Server) — already covers Blob, AI Search, Service Bus management; just configure with Managed Identity - mongodb-js/mongodb-mcp-server — official, use for Atlas environments - qdrant/mcp-server-qdrant — official, adequate for semantic memory use case

    Use with custom extension (add tools to existing server): - neverinfamous/postgres-mcp — deploy as-is; custom tools for business-specific queries can be added - applied-ai-systems/aas-lancedb-mcp — baseline works; may need tuning for our embedding models

    Fork and extend: - LarsCowe/queue-pilot — extend to add Azure Queue Storage data-plane operations (it only covers Kafka/RabbitMQ natively)

    Build from scratch (genuine gap): - Azure Queue Storage (message send/receive/peek/ack) — not in microsoft/mcp - Azure Service Bus data-plane (send/receive messages) — microsoft/mcp only exposes management (queue stats, message counts), not message content operations

    4.3 Benefit of Reuse¶

    By adopting vendor-maintained servers, we automatically receive: - Security patches from MongoDB, Microsoft, Qdrant without our intervention - New tool additions as services evolve (e.g., when Microsoft adds Queue Storage data-plane to Azure MCP Server, we upgrade a container image) - Community-tested tool descriptions and schemas (poor descriptions are the #1 cause of wrong tool selection) - Compliance with each vendor's own auth patterns (Managed Identity for Azure, Atlas service account for MongoDB)

    5. Secret Management: Isolating Credentials from the LLM¶

    The Core Guarantee¶

    The LLM only sees tool inputs and tool outputs — never the tool's internals. Secrets live in the MCP server process memory and never cross the boundary to the LLM context window.

    Pattern 1: Environment Variables Bound at Server Startup¶

    When an orchestrator or gateway starts an MCP server (as a subprocess or container), it passes secrets via environment variables. The LLM never sees these values.

    Example — PostgreSQL MCP Server:

    // mcp-gateway-registry server registration (stored in gateway config, never in LLM context)
{
  "name": "postgres-tools",
  "command": "npx",
  "args": ["-y", "@my-org/postgres-mcp"],
  "env": {
    "POSTGRES_DSN": "postgresql://svc_agent:${SECRET_PG_PASSWORD}@db.internal:5432/a4i_prod",
    "MAX_POOL_SIZE": "10"
  }
}

    Inside the MCP server Python process:

    import os
import psycopg2
from functools import lru_cache

# Bound once at startup — never passed to LLM as a parameter
DSN = os.environ["POSTGRES_DSN"]

@lru_cache(maxsize=1)
def get_pool():
    return psycopg2.pool.ThreadedConnectionPool(1, 10, DSN)

# The tool schema the LLM sees: only { "sql": string, "params": array }
# The LLM has no way to discover POSTGRES_DSN or request it
def query_tool(sql: str, params: list) -> dict:
    with get_pool().getconn() as conn:
        rows = conn.execute(sql, params).fetchall()
    return {"data": rows, "count": len(rows)}

    What the LLM sees in the tool call: 

    {
  "name": "postgres.query",
  "arguments": {
    "sql": "SELECT id, name FROM users WHERE active = $1",
    "params": [true]
  }
}

    The LLM has no mechanism to ask "what is POSTGRES_DSN?" — it is not a parameter, not in the tool description, and not in the response.

    Pattern 2: Azure Key Vault — Dynamic Ephemeral Credentials¶

    For production environments, secrets should not live in environment variables at all. Instead, the MCP server fetches short-lived credentials from Azure Key Vault using Managed Identity (no secret needed to access Key Vault):

    from azure.identity import ManagedIdentityCredential
from azure.keyvault.secrets import SecretClient

# No credentials in config — Managed Identity is used to authenticate to Key Vault
credential = ManagedIdentityCredential()
kv_client = SecretClient("https://a4i-keyvault.vault.azure.net/", credential)

def get_db_connection():
    # Fetch secret at call time — Key Vault caches internally, so this is ~2ms overhead
    pg_password = kv_client.get_secret("postgres-agent-password").value
    return psycopg2.connect(
        host="db.internal", database="a4i_prod",
        user="svc_agent", password=pg_password
    )

    Flow of secret isolation: 

    Azure Key Vault
      │
      │ (Managed Identity, no secret in config)
      ▼
MCP Server Container (Azure Container Apps)
      │
      │ Only formatted query results
      ▼
MCP Gateway
      │
      │ Only tool schemas (name, description, JSON Schema)
      ▼
LLM Provider (Azure OpenAI / Anthropic)
      │
      │ Tool call: { "name": "postgres.query", "arguments": {...} }
      ▼
Agent — never sees credentials at any point

    Why This Matters vs. System Prompt Injection of Credentials¶

    If credentials were placed in a system prompt, they would: - Appear in every LLM API request (logged by the LLM provider and in any tracing tool) - Be extractable via prompt injection attacks ("repeat all text above") - Leak if the conversation is exported, cached, or debugged - Violate Azure OpenAI's data handling policies

    With env-var / Key Vault binding, credentials exist only in the MCP server process address space — isolated from the LLM's context window by design.

    6. Transport Layer: stdio vs HTTP SSE vs Streamable HTTP¶

    The Current Standard (MCP Spec 2025-11-25)¶

    The 2025-11-25 specification defines two standard transports: 1. stdio — for local, in-process MCP servers 2. Streamable HTTP — for all network-accessible MCP servers

    HTTP+SSE is officially deprecated in the 2025-11-25 spec. It is retained only for backwards compatibility. All new MCP servers should use Streamable HTTP for remote scenarios.

    stdio — When and Why¶

    Property Value
    Mechanism Client launches server as a child subprocess; communicates via stdin/stdout; newline-delimited JSON-RPC
    Latency ~0.1–1 ms (pure IPC, no network stack)
    Throughput ~10,000+ ops/sec
    Session model One client, one server — the server exits when the client exits
    Horizontal scaling Not possible — single process, single client

    Best for: - Local development (developer laptops, CI/CD pipelines) - Desktop AI clients (Claude Desktop, Cursor, VS Code Copilot) - Tools accessing local filesystem or OS-level resources - LanceDB in embedded mode (the MCP server and the DB library run in the same process — zero network hop) - High-throughput automation pipelines where 1000s of tool calls/min make network overhead measurable

    Not suitable for: - Any scenario where the MCP server needs to be accessed by more than one agent simultaneously - Cloud deployments behind a load balancer - Services that need to survive an agent restart (the server dies with the client)

    HTTP+SSE — Why It Was Deprecated¶

    HTTP+SSE required two separate endpoints: 1. A POST endpoint for client-to-server requests 2. An SSE stream endpoint for server-to-client responses

    This caused: - Complex routing and CORS configuration - Persistent long-lived connections that don't survive load balancers or serverless platforms (each request had to hit the same server instance) - No stateless operation — horizontal scaling was fundamentally impossible - Proxy/firewall issues with long-lived SSE connections - Connection drops requiring full reconnection and context loss

    HTTP+SSE technically still works for backwards compatibility, but building new tools on it is inadvisable.

    Streamable HTTP — The Correct Choice for Cloud Deployments¶

    Mechanism: Single HTTP endpoint supporting both POST and GET. Client sends JSON-RPC via POST. Server responds with either: - application/json for synchronous responses - text/event-stream (SSE) for streaming/async responses (dynamically chosen per request)

    Key improvements over HTTP+SSE:

    Feature HTTP+SSE Streamable HTTP
    Endpoint count 2 (POST + SSE stream) 1
    Stateless operation No Yes (optional session via MCP-Session-Id header)
    Load balancer compatible No Yes
    Serverless compatible No Yes (Azure Functions, Container Apps scale-to-zero)
    Resumable streams No Yes (Last-Event-ID header)
    Security model Weak Origin header validation, protocol version enforcement

    For our cloud deployments, Streamable HTTP is the right choice for all MCP servers deployed to Azure Container Apps, AKS, or Azure Functions.

    Decision Matrix¶

    Scenario Transport
    Developer local tooling, single user stdio
    LanceDB embedded (in-process DB) stdio
    Claude Desktop / Cursor integration stdio
    Azure Container Apps hosted MCP server Streamable HTTP
    AKS-deployed MCP server, multiple agents Streamable HTTP
    Azure Functions exposed as MCP tool Streamable HTTP
    Behind Azure API Management Streamable HTTP
    Talking to a legacy server (cannot update) HTTP+SSE (backwards compat only)

    7. Hosting Options for MCP Servers and the Gateway¶

    Option A: Docker Compose (Development / Small Deployments)¶

    All MCP servers and the gateway run as Docker containers on a single host. Most appropriate for: - Local development environment - Single-VM pilot deployments - Cost-sensitive scenarios (one VM, ~$20-50/month)

    # docker-compose.yml
services:
  gateway:
    image: agentic-community/mcp-gateway-registry:latest
    ports: ["8080:8080"]
    environment:
      - AUTH_PROVIDER=keycloak
      - KEYCLOAK_URL=http://keycloak:8080
    depends_on: [keycloak, registry-db]

  postgres-mcp:
    image: my-org/postgres-mcp:1.2.0
    environment:
      - POSTGRES_DSN_FILE=/run/secrets/postgres_dsn
    secrets: [postgres_dsn]
    # No port exposure — only accessible to gateway via internal Docker network

  qdrant-mcp:
    image: qdrant/mcp-server-qdrant:latest
    environment:
      - QDRANT_URL=http://qdrant:6333
    depends_on: [qdrant]

  qdrant:
    image: qdrant/qdrant:latest
    volumes: ["qdrant-data:/qdrant/storage"]

  azure-mcp:
    image: mcr.microsoft.com/azure/mcp:latest
    environment:
      - AZURE_CLIENT_ID=${MI_CLIENT_ID}   # Managed Identity
      - AZURE_TENANT_ID=${AZURE_TENANT_ID}

  queue-mcp:
    image: my-org/queue-mcp:1.0.0        # Custom-built (see §8)
    environment:
      - KAFKA_BROKERS=kafka:9092
      - AZURE_SERVICEBUS_CONN_FILE=/run/secrets/sb_conn

  keycloak:
    image: quay.io/keycloak/keycloak:latest

  registry-db:
    image: postgres:16-alpine
    volumes: ["registry-data:/var/lib/postgresql/data"]

secrets:
  postgres_dsn:
    external: true       # Managed outside Docker Compose (e.g., Azure Key Vault, .env)
  sb_conn:
    external: true

    Security note: MCP tool servers are not exposed on public ports. Only the gateway is externally accessible. Tool servers communicate with the gateway over the internal Docker network.

It provides: - Scale-to-zero (zero cost when idle) - Managed ingress with TLS - Managed Identity for Azure Key Vault and Azure services (no secrets in config) - Azure Virtual Network integration (tool servers in private subnet)

    Option C: AKS (Kubernetes) — Production Scale¶

    Two deployment patterns:

    Sidecar pattern — MCP server runs in the same pod as the agent, connected via localhost. Zero network latency, suitable for stdio or localhost Streamable HTTP:

    # Agent pod with MCP server sidecar
spec:
  containers:
  - name: agent-orchestrator
    image: my-org/orchestrator:latest
    env:
    - name: MCP_POSTGRES_URL
      value: "http://localhost:8001/mcp"  # Sidecar, same pod
  - name: postgres-mcp-sidecar
    image: my-org/postgres-mcp:1.2.0
    ports: [{containerPort: 8001}]
    env:
    - name: POSTGRES_DSN
      valueFrom:
        secretKeyRef: {name: postgres-mcp-secrets, key: dsn}

    Dedicated service pattern — MCP servers as independent Kubernetes services; gateway as a shared ingress:

    # Gateway deployment with Workload Identity (AKS best practice)
spec:
  serviceAccountName: mcp-gateway-sa  # Bound to Azure Managed Identity via annotation
  containers:
  - name: gateway
    image: agentic-community/mcp-gateway-registry:latest

    AKS + Workload Identity is the recommended pattern for production — the pod gets a Managed Identity without any secrets in the deployment manifest.

    Option D: Azure Functions (Serverless Tool Endpoints)¶

    Individual tools can be exposed as Azure Functions with the MCP binding, rather than as a standalone server. Best for: - Infrequent calls where scale-to-zero matters (cost: ~$0 at rest) - Tools that call other Azure services and want native SDK bindings - Simple tools that don't require a full container

    # Azure Function as an MCP tool (Python v2 programming model)
import azure.functions as func

app = func.FunctionApp()

@app.function_name("blob_read")
@app.mcp_tool(name="blob.read", description="Read text content of a blob")
def blob_read_tool(tool_input: dict) -> str:
    from azure.storage.blob import BlobServiceClient
    from azure.identity import ManagedIdentityCredential
    client = BlobServiceClient(
        f"https://{STORAGE_ACCOUNT}.blob.core.windows.net",
        credential=ManagedIdentityCredential()
    )
    return client.get_blob_client(
        tool_input["container"], tool_input["name"]
    ).download_blob().readall().decode()

    Tradeoff: Cold starts add 200-800ms latency. Not appropriate for tools called many times per agent turn.

    Latency Reference¶

    Hosting Pattern Transport Typical Overhead
    Sidecar (same pod, localhost) Streamable HTTP ~1–5 ms
    ACA internal subnet Streamable HTTP ~2–10 ms
    AKS ClusterIP service Streamable HTTP ~1–8 ms
    Cross-region Streamable HTTP ~50–200 ms
    Azure Functions (warm) Streamable HTTP ~50–150 ms
    Azure Functions (cold) Streamable HTTP ~300–800 ms

    For interactive agent workflows, LLM inference time (1–30s) dominates. MCP transport overhead is negligible in all hosted scenarios except cross-region.

    8. Tool Abstractions for Target Storage Systems¶

    Design Principles (Common to All Tools)¶

    1. Stateless: Connections injected at server startup via environment variables or Key Vault — never in tool parameters
    2. Allowlisted operations: Named operations only — no raw query/command passthrough
    3. Structured return envelope: { "data": [...], "count": N, "error": null, "_meta": { "tool": "...", "version": "..." } }
    4. LLM-oriented descriptions: Description field written to guide model tool selection, including when not to use the tool
    5. Namespace prefix: postgres., mongo., blob., qdrant., azure_search., lancedb., queue.

    8.1 PostgreSQL Tools (neverinfamous/postgres-mcp extended)¶

    Reuse neverinfamous/postgres-mcp as the base (206 tools, pgvector-aware, connection pooling). Add business-specific query tools as extensions.

    Tool Description Key Parameters
    postgres.query Read-only parameterized SELECT. Never use for writes. sql: str, params: list
    postgres.upsert Insert or update by conflict key. Returns saved record with ID. table: str, record: dict, conflict_col: str
    postgres.vector_search Cosine similarity search via pgvector. Returns top-k rows with distance score. table: str, embedding_col: str, query_vector: float[], top_k: int
    postgres.hybrid_search Combined full-text (tsvector) + pgvector similarity. Ranked by RRF. table: str, text_query: str, query_vector: float[], top_k: int
    postgres.list_tables List accessible tables. Use before querying to understand data model. none
    postgres.describe_table Return columns, types, constraints for a table. table: str

    Notes: Enforce READ ONLY transaction isolation for postgres.query. In Azure: use azure_ai extension for in-database embedding generation, eliminating a round-trip to the embedding service.

    8.2 MongoDB Tools (mongodb-js/mongodb-mcp-server + extensions)¶

    Use the official MongoDB MCP server for Atlas environments. For self-hosted MongoDB, extend neverinfamous/postgres-mcp patterns using pymongo.

    Tool Description Key Parameters
    mongo.find Find documents matching a filter. collection: str, filter: dict, limit: int, projection: dict
    mongo.upsert Insert or update document matching filter. Returns the saved document. collection: str, filter: dict, update: dict
    mongo.aggregate Run aggregation pipeline. Use for grouping, counting, or multi-stage transforms. collection: str, pipeline: list
    mongo.vector_search Atlas Vector Search over embeddings. Requires Atlas, not self-hosted. collection: str, index: str, query_vector: float[], top_k: int, filter: dict
    mongo.list_collections List all accessible collection names. none

    Constraint: Maintain server-side collection allowlist — reject calls to collections not in the allowlist.

    8.3 Azure Blob Storage Tools (microsoft/mcp + custom extensions)¶

    Use the Microsoft Azure MCP Server (microsoft/mcp) for standard Blob operations. Extend with SAS URL generation for media/document access — this is a gap in the official server that we must fill.

    The architecture involves PDFs, images, and binary files. These cannot be returned as raw content in a tool response (size limits, encoding). Instead, agents receive a short-lived signed URL to retrieve or embed the file via a separate HTTP request.

    Tool Description Key Parameters
    blob.list List blob names in a container, filtered by prefix. container: str, prefix: str
    blob.read Read text content of a blob (UTF-8). Use for text files, JSON, Markdown. Do not use for binary files (PDFs, images) — use blob.download_url instead. container: str, name: str
    blob.write Write text or JSON content to a blob. Returns blob URL. container: str, name: str, content: str, content_type: str
    blob.delete Delete a blob. Requires confirm: true to prevent accidental deletion. container: str, name: str, confirm: bool
    blob.get_metadata Retrieve metadata tags and properties without reading content. container: str, name: str
    blob.download_url Generate a short-lived SAS URL (default: 15 min) for downloading a blob. Use for PDFs, images, audio, video, or any binary file. container: str, name: str, expiry_minutes: int
    blob.embedding_url Generate a SAS URL specifically authorized for Azure AI Services to fetch and embed. Returns a URL suitable for passing to an embedding API. Use when the blob is a document or image to be embedded. container: str, name: str

    blob.download_url and blob.embedding_url — how they work:

    from azure.storage.blob import BlobServiceClient, generate_blob_sas, BlobSasPermissions
from azure.identity import ManagedIdentityCredential
from datetime import datetime, timedelta

def download_url(container: str, name: str, expiry_minutes: int = 15) -> dict:
    """
    Generate a SAS URL for downloading a blob. The URL is time-limited.
    The agent never sees the storage account key — it is fetched from Key Vault.
    """
    sas_token = generate_blob_sas(
        account_name=STORAGE_ACCOUNT,
        container_name=container,
        blob_name=name,
        account_key=get_storage_key_from_keyvault(),  # Key Vault, not env var
        permission=BlobSasPermissions(read=True),
        expiry=datetime.utcnow() + timedelta(minutes=expiry_minutes)
    )
    return {
        "url": f"https://{STORAGE_ACCOUNT}.blob.core.windows.net/{container}/{name}?{sas_token}",
        "expires_at": (datetime.utcnow() + timedelta(minutes=expiry_minutes)).isoformat(),
        "blob_name": name
    }

    The agent receives a URL it can pass to Azure Document Intelligence, Azure OpenAI Vision, or an embedding API — it never has direct storage access. The SAS token is signed server-side and expires automatically.

    blob.embedding_url generates a SAS URL with the read permission scoped to a short window (5 minutes default), specifically for passing to embedding/vision APIs. It also enriches the response with content type and blob size metadata to help the agent decide which embedding model to use:

    {
  "url": "https://storage.blob.core.windows.net/documents/report.pdf?sv=...&se=...&sig=...",
  "content_type": "application/pdf",
  "size_bytes": 2097152,
  "expires_at": "2026-03-20T14:35:00Z",
  "recommended_model": "azure-document-intelligence"
}

    8.4 Vector Store: Qdrant vs LanceDB¶

    These serve different deployment contexts and are not mutually exclusive.

    Dimension Qdrant LanceDB
    Deployment model Separate server process (Docker) Embedded library (in-process)
    Memory footprint ~400 MB constant ~4 MB idle
    Query recall ~95% ~88%
    Query latency (p50) ~20–30 ms ~40–60 ms
    Storage model In-memory + disk persistence Disk-first columnar (Lance format)
    Cost at scale Proportional to memory Up to 100x cheaper (cold datasets)
    Multi-modal (images, video) Via custom embeddings Native (text, image, video, audio)
    Filtering Excellent (payload filtering) Good
    Time-travel queries No Yes (versioned format)
    MCP server (official) Yes (qdrant/mcp-server-qdrant) Reference only (lancedb/lancedb-mcp-server)
    Community MCP Good ecosystem applied-ai-systems/aas-lancedb-mcp

    Recommendation: Use both: - Qdrant for the primary knowledge base (high-recall production RAG, shared by multiple agents, server-mode) - LanceDB for agent-local memory, edge deployments, large cold datasets, or anywhere a standalone server is not viable (developer laptop, CI pipeline)

    # Azure Queue Storage MCP tool (data-plane — not in microsoft/mcp)
from azure.storage.queue import QueueServiceClient
from azure.identity import ManagedIdentityCredential

credential = ManagedIdentityCredential()
queue_service = QueueServiceClient(
    f"https://{STORAGE_ACCOUNT}.queue.core.windows.net",
    credential=credential
)

def receive_messages(queue: str, max_count: int = 5, lock_duration_secs: int = 30) -> dict:
    """
    Dequeue messages from Azure Queue Storage. Messages are locked (invisible)
    for lock_duration_secs. Call queue.acknowledge with receipt_handle to confirm
    processing. If not acknowledged within the lock duration, message reappears.
    """
    client = queue_service.get_queue_client(queue)
    messages = client.receive_messages(max_messages=max_count, visibility_timeout=lock_duration_secs)
    return {
        "messages": [
            {"id": m.id, "content": m.content, "receipt_handle": m.pop_receipt,
             "dequeue_count": m.dequeue_count}
            for m in messages
        ]
    }

    9. VectorStore Abstraction Interface¶

    Tools for Qdrant, LanceDB, and Azure AI Search share a common interface to ensure swap-ability:

    from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass
class SearchResult:
    id: str
    text: str
    score: float
    metadata: dict

class VectorStoreAdapter(ABC):
    @abstractmethod
    def search(self, collection: str, query: str, top_k: int = 5,
               filter: dict = None) -> list[SearchResult]: ...

    @abstractmethod
    def upsert(self, collection: str, id: str, text: str,
               metadata: dict = None) -> bool: ...

    @abstractmethod
    def delete(self, collection: str, id: str) -> bool: ...

    @abstractmethod
    def list_collections(self) -> list[str]: ...

# Concrete implementations registered at server startup
class QdrantAdapter(VectorStoreAdapter): ...
class LanceDBAdapter(VectorStoreAdapter): ...        # Embedded, zero network overhead
class AzureAISearchAdapter(VectorStoreAdapter): ...

# MCP tools receive the adapter via DI — same tool schema regardless of backend
class VectorSearchTools:
    def __init__(self, adapter: VectorStoreAdapter):
        self._store = adapter

    @mcp_tool(name="vector.search")
    def search(self, collection: str, query: str, top_k: int = 5) -> list[dict]:
        return [r.__dict__ for r in self._store.search(collection, query, top_k)]

    10. Tool Versioning and Lifecycle¶

    Semantic Versioning Rules¶

    Change Bump Rationale
    Rename or remove a required parameter MAJOR Breaks all existing agent configs
    Change parameter type MAJOR Breaks existing tool calls
    New optional parameter MINOR Backward-compatible addition
    Bug fix, no schema change PATCH No agent behavior change
    Underlying model/embedding upgrade MAJOR Probabilistic output changes even with same schema

    Lifecycle Stages¶

    Draft → Preview → Stable/GA → Deprecated → Sunset

    Deprecated tools emit _meta.deprecation_warning in the response envelope. Sunset date is published 3 months minimum in advance. Agent configurations pin versions ("tool": "postgres.query:1.2.0") so upgrades are always opt-in.

    11. Decision Summary¶

    Decision Choice Rationale
    Tool protocol MCP (JSON-RPC 2.0) Linux Foundation standard, universal framework support, zero cost
    Gateway mcp-gateway-registry from day one Auth, RBAC, audit, and A2A are structural needs — retrofitting creates more debt than the setup overhead
    Community servers to reuse microsoft/mcp, mongodb-js/mongodb-mcp-server, qdrant/mcp-server-qdrant, neverinfamous/postgres-mcp, LarsCowe/queue-pilot Vendor-maintained; free community upgrades
    Custom builds required Azure Queue Storage data-plane, Azure Service Bus data-plane, blob.download_url + blob.embedding_url Genuine gaps in existing servers
    Cloud transport Streamable HTTP HTTP+SSE deprecated in 2025-11-25 spec; Streamable HTTP is load-balancer compatible
    Local/dev transport stdio Zero overhead, no network stack
    Cloud hosting Azure Container Apps (primary), AKS sidecar (for agent-colocated tools) ACA: scale-to-zero + Managed Identity; AKS: low latency for high-frequency tools
    Secret isolation Env var at startup → Key Vault (production) Credentials never enter LLM context window
    Vector store Qdrant (server) + LanceDB (embedded) Qdrant for production RAG; LanceDB for edge/local/large cold datasets
    Swap-ability VectorStoreAdapter ABC One tool schema; swap backend via DI
    Queue abstraction queue.* namespace, multi-broker (Azure Queue, Service Bus, Kafka, RabbitMQ) Unified tool interface across all brokers
