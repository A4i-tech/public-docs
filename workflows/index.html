    🔄 Workflows¶

    Git Workflow¶

    • Branch naming: Since a4i does a lot of cross collaboration with different agencies - the branch naming convention starts with the org-name, followed by the individual-name, the type of task (feature/*. bugfix/*) and a short description. Example: a4i/soumabha/feature/auth-changes
    • Master or Main Branch: a4i/main is usually the main branch across all the codebase repositories. Direct fastforward merge / modification of commit history is not permitted on this branch and has special protected privilege
    • Contribution: to contribute to changes, a new branch must be created from the latest master (a4i/main) and a pull request is to be used to merge changes.
    • Compliance and Testing: Every pull request requires at least 1 reviewer to sign off to the changes. The requestor is also expected to pass all the necessary github actions workflow like secret-detection, unit-testing, code and security scanning.

    Issue Tracking¶

    • Uses GitHub Issues
    • Planning is via Project board
    • Project Labels: SEEDS, Shiksha-Copilot, ASHABot, General : to indicate area of impact.
    • Labels: bug, enhancement, retro, infra: to indicate quality and volume.

    CI/CD¶

    • GitHub Actions run lint/tests on PR
    • Staging deployment happens via a4i/main branch

    Code Style Standards¶

    General Rules¶

    • Quotes: Use double quotes (") for all strings in JavaScript
    • Semicolons: Always use semicolons at the end of statements
    • Trailing Commas: Do NOT use trailing commas in objects, arrays, or function parameters
    • Line Width: Maximum 100 characters per line
    • Indentation: 2 spaces (enforced by Prettier)

    Example¶

    // ✅ CORRECT
const user = {
    name: "John Doe",
    email: "john@example.com",
    role: "admin",
};

function greet(name) {
    console.log("Hello, " + name);
}

// ❌ INCORRECT
const user = {
    name: "John Doe",
    email: "john@example.com",
    role: "admin",
};

function greet(name) {
    console.log("Hello, " + name);
}

    Linting and Formatting¶

    All projects use ESLint for linting and Prettier for code formatting.

    Configuration Files¶

    Node.js Backend Projects (CommonJS)¶

    • eslint.config.js - ESLint flat config (v9+)
    • .prettierrc - Prettier configuration

    React Projects¶

    • .eslintrc.json - ESLint configuration extending react-app and prettier
    • .prettierrc - Prettier configuration

    Auto-Formatting¶

    VS Code is configured to auto-format on save:

    • Prettier runs automatically when you save files
    • ESLint auto-fixes issues on save
    • Configuration in .vscode/settings.json

    Manual Commands¶

    # Lint entire project
npm run lint

# Fix all linting and formatting issues
npm run lint:fix

# Fix a specific file
npm run fix:file -- src/index.js

# Fix multiple files
npm run fix:file -- src/index.js src/config/env.js

    Pre-Execution Hooks¶

    Linting runs automatically before:

    • Starting the dev server: npm start → runs lint:fix first
    • Running tests: npm test → runs lint:fix first

    This ensures code is always properly formatted before execution.

    Development Workflow¶

    1. Setting Up a New Project¶

    # Clone the repository
git clone <repository-url>
cd <project-directory>

# Install dependencies
npm install

# Start development server
npm start

    2. Before Making Changes¶

    # Create a new branch
git checkout -b feature/your-feature-name

# Ensure dependencies are up to date
npm install

    3. During Development¶

    • Write code following the style guide
    • Save frequently - auto-formatting will apply
    • Run tests regularly: npm test
    • Check for errors in the terminal and VS Code Problems panel

    4. Before Committing¶

    # Run linting manually (optional, as it runs on pretest/prestart)
npm run lint:fix

# Run all tests
npm test

# Check coverage (should be generated automatically)

    Common Scripts¶

    All SEEDS projects include these standard npm scripts:

    Script Description
    npm start Start the development server (auto-lints first)
    npm test Run all tests with coverage (auto-lints first)
    npm run lint Check for linting issues (no fixes)
    npm run lint:fix Fix all linting and formatting issues
    npm run fix:file -- <path> Fix specific file(s)
    npm run build Build for production (React projects)
    npm run dev Start with nodemon (backend projects)
